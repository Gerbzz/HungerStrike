# HungerStrike screenshot provenance

The README displays `assets/screenshots/hungerstrike-kitchen-current.png`, a new uncomposited 1440 × 900 frame saved by the current HungerStrike Windows desktop app on October 14, 2026. SHA-256: `50D8D016360E5F4B92043EF61B4AEE9E2643750A9019DBCBA0A7F36C57FDD21E`. The image was visually inspected. It shows the app's 3D kitchen and confirmed stock from first-party synthetic receipt fixtures; no real receipt, client data, or personal workstation path appears in it.

The desktop source was built from public source revision `a55700a6b36b9d390f678b77da43cb43f23bf09f` with `cargo build --offline --locked -p hungerstrike-rust-desktop -j 1` and an existing local target cache. The build completed in 26.44 seconds. The executable SHA-256 is `C8B26E6EC4C5791902246053DF3FA84B3CBE2F56A9CFEA9517A86BCC2BCB480C`. The subsequent public commit `c4b1d3d` changed only `.gitignore`, `README.md`, and this documentation; it did not change the app source. The binary depfile points to the public checkout's Rust source and included fixture files.

The capture set `HUNGERSTRIKE_DATA_DIR` to an isolated workspace directory, `HUNGERSTRIKE_CAPTURE_DEMO=kitchen`, and `HUNGERSTRIKE_CAPTURE_PATH` to a local PNG. The app wrote the frame with its built-in Bevy screenshot path. The PNG reached a stable 701,523 bytes before the capture process was stopped; the app was not claimed to have exited naturally. Local SQLite data and launch logs stayed outside Git under the ignored `capture/` directory.

Sandboxed launch attempts faulted in `ntdll.dll` with Windows code `0xC0000008` shortly after window creation, as confirmed by Windows Application Error events. A reviewed normal-access launch of the same exact-source binary completed the screenshot. The different execution context appears to explain the launch failure; this is an inference, not a diagnosed app-code defect.

Receipt, Meals, and Spending were independently recaptured from the same current-source executable with separate isolated synthetic databases. Their PNGs were byte-for-byte identical to the existing `docs/verification` images, so those files were retained without duplication: receipt SHA-256 `9B6AAB21B6718E80AE7C99A6345B04D08C7F20C28E388F5983F2E0D6C3B33D4E`, meals `7DAEE2457B9BA3D0270C45CF698CC34A36F72227482F3A7755258DB8EF12325C`, spending `EB23347A253530EA4E68F75B45D7D09C6D78B3C2E1A5DCC0F875B55B38993472`.

These captures verify startup, synthetic state rendering, and the screenshot path. They do not establish native mouse or keyboard workflows, OCR, backup restore, accessibility, wider receipt acceptance, or operation on other devices. The earlier [verification record](../verification.md) describes separate tests and their limits; no full test suite was rerun for this screenshot publication.
